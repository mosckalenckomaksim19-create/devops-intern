# Как разобраться и защитить работу

## Оценка сложности с твоей базой

Задание выполнимо с пошаговой помощью. Linux, Docker, Git/GitLab и сети уже дают нужный фундамент. Ansible поможет читать декларативный YAML, хотя сам Ansible здесь не требуется. Пробелы в Kubernetes существенны для понимания практики, но нужный объём ограничен Pod, Deployment, ReplicaSet, Service, labels и port-forward. По SQL нужно понять соединения таблиц и фильтрацию групп; устанавливать БД для приложения не нужно.

Практический ориентир по времени — несколько учебных сессий: 1–2 часа на теорию, 1–2 на приложение/Docker, 2–4 на Kubernetes и проверку, ещё 1–2 на оформление. Это оценка, а не обещание срока: настройка WSL, загрузки и диагностика могут занять дольше.

Готовность к сдаче определяется не тем, что YAML скопирован, а тем, что ты можешь пройти цепочку от браузера до процесса и объяснить каждое число порта.

## Объяснение за одну минуту

«Я сделал HTTP-приложение на Python, которое слушает 0.0.0.0:32777. Оно отвечает Hello world и показывает имя экземпляра. Собрал Docker-образ и опубликовал его в Docker Hub. В локальном кластере Minikube Deployment поддерживает два Pod с этим образом. Service типа ClusterIP выбирает их по метке app: hello-world и направляет свой порт 80 на порт приложения 32777. Для доступа из браузера я запускаю port-forward локального порта 32777 к Service. Этот туннель выбирает одну реплику; доступ через сам ClusterIP внутри кластера проверяю отдельно».

Используй прошедшее время про публикацию и развёртывание только после того, как действительно выполнишь эти шаги.

## Ключевые вопросы

### Почему Python без Flask?

ТЗ допускает любой язык. Для статического ответа достаточно стандартной библиотеки Python. Меньше зависимостей — проще понять сборку. Это осознанное упрощение учебного приложения; для полноценного сервиса выбор веб-стека был бы другим.

### Образ и контейнер — одно и то же?

Образ — шаблон с файловой системой и настройками запуска. Контейнер — запущенный экземпляр с процессом и собственным изменяемым слоем. В Docker Hub публикуется образ, а не живой процесс.

### Чем Pod отличается от контейнера?

Pod — минимальная единица размещения Kubernetes: один или несколько тесно связанных контейнеров с общей сетью и возможностью общих volumes. В этой работе в каждом Pod один контейнер.

### Чем Deployment отличается от Pod?

Pod запускает контейнеры. Deployment описывает желаемое состояние и обновления, управляя ReplicaSet. ReplicaSet следит, чтобы число Pod соответствовало желаемому. При удалении Pod появится новый, с новым именем и обычно новым IP.

### Зачем Service, если есть IP Pod?

IP Pod меняются при пересоздании. Service даёт устойчивое имя и виртуальный IP, а набор готовых адресов Pod обновляется через EndpointSlice. Service не является отдельным контейнером и не создаёт реплики.

### Почему две реплики?

Это условие задания и возможность показать несколько экземпляров за общим Service. Отказ отдельного Pod можно пережить с оставшейся готовой репликой. В одноузловом Minikube падение узла затронет обе реплики; полной отказоустойчивости инфраструктуры здесь нет.

### Почему порт 80, если ТЗ требует 32777?

Процесс приложения слушает 32777. Число 80 относится к Service внутри кластера, который направляет соединение на 32777 у Pod. Локальный порт браузера мы тоже выбрали 32777. `32777:80` в port-forward означает «локальный порт : порт Service».

### EXPOSE и containerPort открывают порты?

Нет. Сокет открывает процесс в app.py. EXPOSE документирует порт в образе, containerPort описывает его в Pod и позволяет дать ему имя. Docker `-p`, Service и port-forward решают разные задачи доступа.

### Почему при обновлении страницы не меняется Instance?

Port-forward к Service выбирает один Pod и не балансирует каждый HTTP-запрос между всеми репликами. Для проверки Service нужно обратиться к нему из кластера; для проверки каждой реплики можно сделать отдельный port-forward к её Pod.

### Чем readiness отличается от liveness?

Readiness отвечает «можно ли направлять сюда запросы?» Неуспешная проверка исключает Pod из обычных готовых адресов Service. Liveness отвечает «жив ли процесс?» После заданного числа неудач kubelet перезапускает контейнер. В нашем небольшом приложении используется один простой endpoint; в реальных системах критерии могут различаться.

### Почему приложение не сохраняет данные?

Для hello-world хранение не требуется. Состояния между репликами нет. Если появятся пользовательские данные, понадобится отдельно выбрать постоянное хранилище, БД и способ совместного доступа, а не полагаться на локальную файловую систему контейнера.

## Самопроверка после успешного запуска

1. Без подсказки объясни разницу трёх сущностей: image, container, Pod.
2. Найди в YAML селектор Service и совпадающую метку Pod.
3. Покажи два Pod с `READY 1/1` и Deployment с `READY 2/2`.
4. Найди обе реплики в EndpointSlice и сопоставь адреса с `get pods -o wide`.
5. Расскажи, почему два Pod слушают одинаковый порт без конфликта.
6. Объясни SQL-пример с оплаченной суммой: что отсеивает WHERE и что HAVING.

Необязательный опыт восстановления в своём учебном кластере: открой `kubectl get pods -l app=hello-world -w`, в другом окне удали один конкретный Pod командой `kubectl delete pod ИМЯ` и посмотри появление нового. Не удаляй Deployment. Если удалён выбранный для туннеля Pod, заново запусти port-forward. Этот опыт показывает работу контроллера, а не сохранение соединений при любых сбоях.
